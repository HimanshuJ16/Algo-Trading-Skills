# Workflows for ASIC Automated Order Processing

Rule references are to the ASIC Market Integrity Rules (Securities Markets) 2017, Part 5.6,
read with RG 241 (2 August 2022). See `standards.md` for the full rule map, the currency note
and the source links.

## 1. System initialisation

Construct `AsicMarketIntegrityConfig` with hard limits approved by the firm's compliance
officer. Construction validates that `max_order_value_aud` and `max_order_volume` are positive
and finite and that `max_price_deviation_pct` lies in `(0.0, 1.0]`; anything else raises
`ValueError`, because a disabled control is a misconfiguration (RG 241.45). The config is
frozen — it cannot be widened in place afterwards.

Record the *justification* for each number alongside it. Part 5.6 prescribes no thresholds
(RG 241.36); the documentation supporting the Rule 5.6.6 certification is where the choice has
to stand up.

Construct `AsicKillSwitchManager(cancel_series_callback=...)` with a callback wired to the
order management system's bulk-cancel path. Without one, the Rule 5.6.3(1)(e)(ii)/(iv)
cancellation limb is not satisfied by this component and every halt will record
`NOT_CONFIGURED`.

## 2. Pre-trade hook

Every order generated by the strategy engine must pass synchronously through
`AsicAopPreTradeFilter.run_checks()` *before* being serialised to the FIX connection. The
check order is:

1. halt state — global, then the order's authorised person, client, product, market, algorithm;
2. non-finite / non-numeric input (`NaN`, `±Inf`, `bool`, `Decimal`, strings);
3. field sanity — positive quantity and price;
4. reference price positive;
5. volume limit;
6. value limit;
7. price deviation, compared by multiplication (`abs(price - ref) > pct * ref`).

Populate `client_id`, `authorised_person_id`, `algorithm_id` and `market` on the
`AopOrderRequest` wherever you intend to be able to suspend AOP at that granularity — a halt
scoped to an identity the orders never carry is inert.

## 3. Re-check at the point of send

`ComplianceResult` is a point-in-time decision stamped with `checked_at_unix`. Rule
5.6.3(1)(d) requires suspension to be *immediate*, so a halt raised between the check and the
send must stop the message. Re-read `halt_blocking` immediately before writing to the session,
inside the same critical section as the send if the architecture has one.

## 4. Audit capture

Persist every returned `ComplianceResult` — `is_compliant`, `rejection_code`, `order_id`,
`checked_at_unix`, `reason` — to the firm's audit store, approvals as well as rejections. This
feeds the Part 5.6 monitoring and exception-reporting expectations at RG 241.81-241.87, under
which exception reports should be monitored regularly and at least daily (RG 241.87).

This module performs no pattern detection. Real-time surveillance across a *series* of
messages (RG 241.82) and post-trade analysis of historic order and trading patterns
(RG 241.84) are separate systems fed by this audit stream.

## 5. Emergency halt

Classify the problem before choosing the scope:

- **Traced to one source** — a particular authorised person, client, product, market or
  algorithm (RG 241.53): call
  `trigger_scoped_halt(AopHaltScope.ALGORITHM, "algo-7", reason=..., actor=...)`. Prefer this.
  Halting all AOP because one algorithm misbehaved is itself disruptive to the participant's
  other clients.
- **Systemic** — the AOP system as a whole, or an ASIC direction under Rule 5.6.12 to cease or
  suspend AOP: call `trigger_kill_switch(reason=..., actor=...)`.

Neither call is ever refused for a missing reason or actor: blocking a halt because its
paperwork is incomplete would be the worse failure. Missing attribution is logged as a warning
so the record can be completed retrospectively.

On trigger, the manager invokes `cancel_series_callback` with the `AopHaltRecord` to discharge
Rule 5.6.3(1)(e)(ii)/(iv) against messages already in the market, and records the outcome on
the audit entry:

- `COMPLETED` with `cancelled_message_count`;
- `FAILED` with the error text — escalated at `CRITICAL`, because this is the outcome where
  messages are still live in the market during a breach. Treat it as an incident, not a log
  line;
- `NOT_CONFIGURED` — no callback was supplied.

A raising callback never prevents the halt from applying.

## 6. Resume

Reset only after root-cause review. `reset_kill_switch(reason=..., actor=...)` and
`release_scoped_halt(scope, value, reason=..., actor=...)` both:

- refuse a blank or whitespace reason or actor, append a `RESET_REFUSED` audit entry and
  return `False`, leaving the halt in force (RG 241.44 — administrator-level changes only
  after authorisation by a qualified person);
- return `False` if no such halt was active;
- return `True` only when a halt was actually released.

Check the return value. A global reset does **not** release scoped halts — release each
deliberately, so an algorithm suspended for cause is not silently readmitted by an unrelated
system-wide resume.

## 7. Filter parameter changes

Change parameters only through
`replace_config(new_config, authorised_by="...", reason="...")`. It validates the replacement,
refuses blank attribution, and appends a `FilterParameterChange` capturing the previous and
replacement configs with a timestamp — satisfying the Rule 5.6.3(1)(a) obligation to record
any change to filters or filter parameters, including intra-day changes (RG 241.43).

Before implementing, decide whether the change is *material* for Rule 5.6.8, which requires the
review to happen **before** the change goes in. RG 241.174 lists relevant examples, including a
change that increases the risk of orders creating or appearing to create a disorderly market
(174(h)), one that increases the risk of a high order-to-trade ratio (174(i)), and a series of
incremental changes that together amount to a material change (174(e)).

Where a temporary widening is approved, schedule its reversal at the time you make it.

## 8. Certification and periodic review

Out of scope for this module, but part of the same obligation set:

- **Initial certification** before using the system for AOP on a market — Rule 5.6.6 (with
  Rules 5.6.4 and 5.6.5).
- **Material change review** before implementing a material change — Rule 5.6.8.
- **Annual review** by an appropriately qualified person, of policies, procedures and system
  design documentation — Rule 5.6.8A. Not required for a system whose material changes were
  reviewed under Rule 5.6.8 within the 12 months before the annual review date
  (RG 241.185). One review covers multiple AOP systems (RG 241.186).
- **Annual notification to ASIC** — Rule 5.6.8B. The annual review date is **1 November each
  calendar year**, and the notification must be given **within 10 business days** of it
  (RG 241.188).

Confirm at each review that the filter parameters, the halt scopes and the cancellation
callback wiring are still correct, and that `parameter_audit_log` and `audit_log` have been
persisted for the period under review.
