# Standards for Algo Trading Disclosure

This reference separates regulatory obligations from implementation controls.
Confirm the current venue rulebook, broker specification, and legal
interpretation before production deployment.

## Regulatory Touchpoints

| Scope | Practical requirement | Engineering implication |
|---|---|---|
| EU MiFID II Article 48(8) | Trading venues must be able to identify algorithmic orders generated by a member or participant. | Preserve an algorithmic-order flag or identifier through the venue adapter; do not assume one universal FIX field. |
| EU RTS 6 (Commission Delegated Regulation (EU) 2017/589) | Firms must maintain algorithmic-trading governance, testing, controls, records, and the ability to identify relevant algorithms and persons. | Keep a versioned approval record, deployment evidence, durable audit logs, and a fail-closed pre-trade gate. |
| EU transaction reporting (Commission Delegated Regulation (EU) 2017/590, Articles 8-9) | Algorithm identification and trader/client identification fields apply to transaction reports and use defined code formats. | Keep transaction-reporting identifiers distinct from venue order tags and validate both at their respective boundaries. |
| India SEBI framework and exchange procedures | Exchange-issued algo identifiers and tagging requirements are implemented through current SEBI and exchange operating procedures. | Make registration status and venue scope explicit; do not copy EU assumptions into NSE, BSE, or another venue adapter. |

## Engineering Contract

| Control | Required behavior |
|---|---|
| Classification | `is_algorithmic` is explicit and owned by an upstream classification process. |
| Manual orders | Require `trader_id`; reject a contradictory `algo_id`. |
| Algorithmic orders | Require an exchange-facing `algo_id` and an `APPROVED` registry status. |
| Scope | If a registry record lists venues or a version, require an exact match. |
| Child orders | Preserve the parent algorithm identifier and reject a supplied mismatch. |
| Unknown state | Unknown, malformed, pending, deprecated, or suspended records fail closed. |
| Auditability | Emit a stable reason code, order ID, algorithm ID when available, and registry status. |
| Registry consistency | Snapshot the validated registry at engine construction; update it through a controlled deployment process. |

## Venue and FIX Mapping

The compliance engine validates the logical `algo_id`; the venue adapter owns the
mapping to the broker or exchange field. Never hard-code a tag number such as
`25013` as a universal MiFID II requirement. Confirm the current venue
specification, test the serialized message, and retain the mapping version with
the deployment record.

## Registration State Model

Use explicit states such as `PENDING`, `APPROVED`, `SUSPENDED`, `DEPRECATED`, and
`REJECTED`. Only `APPROVED` is executable. A status transition must be reviewed,
versioned, auditable, and coordinated with the strategy deployment manifest.
