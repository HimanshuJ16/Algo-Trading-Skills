# Standards — network-interface-level-tick-timestamping

## Control-message layouts (Linux UAPI)

Every figure below is transcribed from the Linux kernel UAPI headers and the kernel
networking documentation; sources are listed at the end of this file. `cmsg_level` is
`SOL_SOCKET` for all three.

| `cmsg_type` (asm-generic) | Socket option | Payload struct | Fields | Size LP64 | Size ILP32 |
|---|---|---|---|---|---|
| `SCM_TIMESTAMP` = 29 (`_OLD`), 63 (`_NEW`) | `SO_TIMESTAMP` | `struct __kernel_old_timeval` / `struct __kernel_sock_timeval` | `tv_sec`, `tv_usec` | 16 B | 8 B (`_OLD`), 16 B (`_NEW`) |
| `SCM_TIMESTAMPNS` = 35 (`_OLD`), 64 (`_NEW`) | `SO_TIMESTAMPNS` | `struct timespec` / `struct __kernel_timespec` | `tv_sec`, `tv_nsec` | 16 B | 8 B (`_OLD`), 16 B (`_NEW`) |
| `SCM_TIMESTAMPING` = 37 (`_OLD`), 65 (`_NEW`) | `SO_TIMESTAMPING` | `struct scm_timestamping` / `scm_timestamping64` | `timespec ts[3]` | 48 B | 24 B (`_OLD`), 48 B (`_NEW`) |

`SCM_TIMESTAMP`, `SCM_TIMESTAMPNS` and `SCM_TIMESTAMPING` are `#define`d to the
corresponding `SO_*` value, and userspace selects the `_OLD` or `_NEW` numbering by
`sizeof(time_t) == sizeof(__kernel_long_t)`.

**These numbers are architecture-dependent.** The table above is `asm-generic`, shared
by x86-64, arm64, mips and alpha. sparc uses `SO_TIMESTAMP_OLD 0x001d`,
`SO_TIMESTAMPNS_OLD 0x0021`, `SO_TIMESTAMPING_OLD 0x0023`; parisc uses `0x4012`,
`0x4013`, `0x4020`. The engine accepts explicit overrides for this reason.

## `struct scm_timestamping` slot semantics

| Slot | Contents |
|---|---|
| `ts[0]` | Software timestamp (kernel receive path), when requested and available |
| `ts[1]` | **Deprecated.** Formerly hardware timestamps converted to system time |
| `ts[2]` | Hardware timestamp as generated by the adapter |

The kernel documentation states: *"At least one field is non-zero at any time. Most
timestamps are passed in ts[0]. Hardware timestamps are passed in ts[2]."* An all-zero
slot is therefore an unfilled slot, not an epoch timestamp.

## `SOF_TIMESTAMPING_*` receive flags

| Flag | Value | Meaning |
|---|---|---|
| `SOF_TIMESTAMPING_RX_HARDWARE` | `1<<2` | Request rx timestamps generated by the network adapter |
| `SOF_TIMESTAMPING_RX_SOFTWARE` | `1<<3` | Request rx timestamps when data enters the kernel |
| `SOF_TIMESTAMPING_SOFTWARE` | `1<<4` | Report any software timestamps when available |
| `SOF_TIMESTAMPING_RAW_HARDWARE` | `1<<6` | Report hardware timestamps as generated by `SOF_TIMESTAMPING_RX_HARDWARE` |

## Engineering standards

| Requirement | Standard |
|---|---|
| Type-based classification | The capture point MUST be determined from `cmsg_type`, never from the control-buffer length. On LP64 a `timespec` and a `timeval` are both 16 bytes, so a size test cannot distinguish nanoseconds from microseconds and silently under-reports the sub-second component by 1000×. |
| Hardware slot | A `HARDWARE_NIC` label MUST come from a non-zero `ts[2]` of a `SCM_TIMESTAMPING` message. `ts[0]` is the kernel software timestamp; reading it and labelling it hardware misrepresents the capture point. |
| Timebase separation | Hardware timestamps are NOT converted to system time by the kernel. `T_app − T_hw` MUST be reported as a cross-timebase figure until `phc2sys`/`sfptpd` disciplines the PHC against `CLOCK_REALTIME`. |
| Signed delta | The capture delay MUST be reported signed. Clamping at zero destroys the observable signature of an undisciplined PHC. |
| Integer nanoseconds | Timestamps MUST be integer nanoseconds. IEEE 754 binary64 has a 53-bit significand, so the representable spacing at a ~1.7e18 ns epoch is 256 ns — coarser than the effect being measured. |
| No false software timestamps | `SO_TIMESTAMP`/`SO_TIMESTAMPNS` MUST NOT be enabled on a socket that also requests `SO_TIMESTAMPING` with `SOF_TIMESTAMPING_SOFTWARE`; the kernel then fabricates a substitute timestamp into `ts[0]`. |
| Capability verification | Hardware capture MUST be confirmed from the adapter's advertised capabilities (`ethtool -T`), not inferred from a populated control message — the message is delivered regardless. |
| Control buffer sizing | `recvmsg` MUST allocate `CMSG_SPACE(48)` on LP64. An undersized `ancbufsize` truncates the control message and the hardware slot is the trailing part that is lost. |
| Portability | The `SO_*`/`SCM_*` numbers MUST be configurable. CPython exports none of them, and sparc/parisc use different values from `asm-generic`. |

## Platform notes

| Surface | Behaviour | Note |
|---|---|---|
| CPython `socket` module | Exports no `SO_TIMESTAMP*`, `SCM_TIMESTAMP*` or `SOF_TIMESTAMPING_*` constant on any platform (verified against `Modules/socketmodule.c` on `main`). | `hasattr(socket, "SO_TIMESTAMPNS")` is always `False`, so any activation path guarded on it never runs. The numeric value must be passed to `setsockopt` directly. |
| PTP hardware clock (PHC) | An independent clock on the adapter. `ptp4l` disciplines it to a grandmaster; `phc2sys`/`sfptpd` relates it to the system clock. | Without that second step, subtracting a hardware timestamp from `CLOCK_REALTIME` measures a clock offset, and can be negative. |
| Solarflare / AMD adapters | OpenOnload exposes its own `onload_timestamping` receive path in addition to the socket API, and `sfptpd` disciplines adapter and system clocks. | Bypass-path timestamps do not arrive as `recvmsg` ancillary data. This skill deliberately encodes no vendor accuracy figure — datasheet *resolution* is not end-to-end *accuracy*, which is set by the whole traceability chain and must be measured on the deployed host. |

## Regulatory note

This skill decodes a timestamp; it does not audit one. Where a recorded event time must
withstand a MiFID II RTS 25 clock-traceability review, the applicable divergence and
granularity bounds, the documented timestamping point and the annual review are covered
by `hardware-timestamping-vs-software-timestamping-accuracy`. No figure in this file is
a regulatory threshold.
